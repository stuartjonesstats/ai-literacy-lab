# Content Roadmap

This roadmap defines the first full content pass for AI Literacy Lab.

## Content Design Standard

Each module should include:

- a cold-open scenario
- a learner first move
- a realistic artifact
- a complication
- a concept reveal
- a second attempt or rewrite
- a self-check or rubric
- a transfer heuristic
- an accuracy note

The goal is not to make every module equally elaborate. The goal is to create a coherent arc where learners repeatedly practice judgment under uncertainty.

## Module Interaction Intensity

| Module | Interaction Intensity | Reason |
| --- | --- | --- |
| 1. What AI is good and bad at | Medium | Learners need a fast first experience of context-dependent classification. |
| 2. Why confident answers can be wrong | High | Learners need to feel how polished output can outrun evidence. |
| 3. Data, privacy, and confidentiality | High | Learners need to practice boundary-setting, redaction, and safer alternatives. |
| 4. Bias, fairness, and representational harm | Medium-high | Learners need to notice subtle representational harm without relying on cartoon examples. |
| 5. Human accountability and review | High | Learners need to distinguish meaningful review from ceremonial review. |
| 6. Using AI well in everyday work | Medium | Learners need a practical workflow design pattern. |
| 7. Risk classification and escalation | High | Learners need branching ambiguity and defensible escalation decisions. |
| 8. Capstone | Very high | Learners need to integrate the full course through a realistic simulation. |

## Suggested Build Order

1. Complete Module 3 as an interactive data-boundary lab.
2. Build Module 7 as a branching risk-escalation fork.
3. Build Module 5 as a human-review workflow simulator.
4. Expand the capstone once Modules 1, 2, 3, 5, and 7 have working patterns.
5. Fill Modules 4 and 6 with lighter but polished interactions.

## Accuracy Standard

Prefer synthetic case packets wherever possible. A synthetic packet lets the learner inspect the evidence directly, and it lets maintainers verify the scenario without relying on time-bound facts, legal interpretation, or vendor behavior.

When a module needs external claims, record them in `research/` before making them learner-facing.
